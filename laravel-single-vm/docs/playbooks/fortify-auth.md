# Extend Fortify sign-in

Use when a page needs a signed-in user, editor or admin, or the owner wants to change registration, verification or two-factor sign-in. Paths below start in `apps/web`.

1. Start with `routes/web.php`, `config/fortify.php` and `app/Providers/FortifyServiceProvider.php`. Fortify already handles session login, logout, registration, password resets and opt-in two-factor authentication with password and enrollment confirmation. Reuse its actions and Vue pages. Keep the existing web guard, CSRF protection and login throttling.
2. For an editor-only page, add a migration in `database/migrations` for a boolean `users.is_editor` defaulting to false. Add its boolean cast and property annotation to `app/Models/User.php`. Keep privileges outside the model's fillable fields and all public account forms. Grant the flag only to the intended existing account through a trusted server-side operation. In `app/Providers/AppServiceProvider.php`, define a gate in `boot()`, e.g. `Gate::define('view-members', fn (User $user): bool => $user->is_editor);`. Apply `['auth', 'can:view-members']` to the named route in `routes/web.php` that renders the Vue page. Use the same guard on its writes. For the first admin, follow the token-protected setup in `docs/playbooks/admin-content.md`. For ordinary members-only access, `auth` suffices.
3. To close registration, remove `Features::registration()` from the features array. Remove the sign-up links and Wayfinder imports in `resources/js/pages/Welcome.vue` and `auth/Login.vue` (under the same pages directory). Remove the unused `auth/Register.vue` which imports the generated register action. Search for remaining references after route generation, including tests. Replace registration success expectations with coverage for both GET and POST to the disabled endpoint.
4. Enable only the requested Fortify features. Email verification is off. To require it, add `Features::emailVerification()`, implement `Illuminate\Contracts\Auth\MustVerifyEmail` on User, wire `Fortify::verifyEmailView` to a new verification notice page with a resend form, and apply `auth` and `verified` to the protected routes. Removing that feature also requires removing the verification requirement and its UI. To disable two-factor, remove the corresponding feature entry and reconcile the security settings, challenge page, generated route imports and tests. Preserve existing user records.
5. Check mail delivery before promising either verification or password resets. The starter supplies no delivery transport. `config/mail.php` defaults to the log mailer, so these messages do not reach an inbox until the operator configures a real mailer. Keep reset links and mail credentials private.
6. In `tests/Feature`, assert the guest redirect to login, 403 for a signed-in user without the flag and the expected Inertia page for an editor. Check disabled registration rejects both requests without creating an account. Apply the migration with `project_check` migrations, run `project_check` verify, and open the members page and registration URL signed out in the preview.
