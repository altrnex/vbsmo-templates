# Extend Fortify sign-in

Use when a page needs sign-in or a specific role, or the owner wants to change registration, verification or two-factor sign-in. Application paths are relative to `apps/web`. Playbook paths (`docs/playbooks/`) are relative to the project root.

1. Start with `routes/web.php`, `config/fortify.php` and `app/Providers/FortifyServiceProvider.php`. Fortify already handles session login, logout, registration, password resets and opt-in two-factor authentication with password and enrollment confirmation. Reuse its actions and Vue pages. Keep the existing web guard, CSRF protection and login throttling.
2. Name the flag for the role and the gate for the action. For admins use `is_admin` and `manage-content`. Add the boolean flag to `users` in a new migration with default false. Add its boolean cast and property annotation to `app/Models/User.php`. Exclude the flag from fillable fields and registration and profile inputs. In `app/Providers/AppServiceProvider.php`, define the matching gate in `boot()`, e.g. `Gate::define('view-members', fn (User $user): bool => $user->is_editor);`. Apply `auth` and the matching `can:` middleware to every protected read and write in `routes/web.php`. For ordinary members-only access, `auth` suffices. Create the first admin using the token-protected setup in steps 2–3 of `docs/playbooks/admin-content.md`. Grant the role through an admin-only action.
3. To close registration, remove `Features::registration()` from the features array. Under `resources/js/pages`, remove the sign-up links and Wayfinder imports in `Welcome.vue` and `auth/Login.vue`, then remove the unused `auth/Register.vue` and its store import. In `tests/Feature/Auth/RegistrationTest.php`, replace the feature-enabled skip and success tests with GET and POST checks against the literal `/register` path. Search `resources/js` and `tests` for remaining register callers. Run the build to regenerate Wayfinder output, then run `vue-tsc --noEmit` to catch stale imports.
4. Enable only the requested Fortify features. Email verification is off. To require it, add `Features::emailVerification()`, implement `Illuminate\Contracts\Auth\MustVerifyEmail` on User, wire `Fortify::verifyEmailView` to a new verification notice page with a resend form, and apply `auth` and `verified` to the protected routes. Removing that feature also requires removing the verification requirement and its UI. To disable two-factor, remove the corresponding feature entry and reconcile the security settings, challenge page, generated route imports and tests. Preserve existing user records.
5. Check mail delivery before promising either verification or password resets. The starter supplies no delivery transport. `config/mail.php` defaults to the log mailer, so these messages do not reach an inbox until the operator configures a real mailer. Keep reset links and mail credentials private.
6. In `tests/Feature`, assert the guest redirect to login, 403 for a signed-in user without the flag and the expected Inertia page for a user with the flag. Check disabled registration rejects both requests without creating an account. Apply the migration with `project_check` migrations, run `project_check` verify, and open the protected page and registration URL signed out in the preview.
